# PunchPace

Audio-guided routine timer (reps, timed blocks, sequences, boxing combos) for people who do the same routines daily or weekly. Installable PWA, works offline, optional sign-in to sync. Open source; the goal is an app that is safe to use and easy to contribute to.

Live: https://punchpace.app (Firebase Hosting). The old addresses, https://agepoor.github.io/repflow/ (the repo is still called `repflow`, the app's old name) and https://workout-pacer.web.app, still get every deploy but forward to punchpace.app with the device's data (`core/move.js`, `ui/move.js`; `#stay` keeps the old one open).

## Commands

No bundler: plain ES modules, served as static files. `package.json` only holds the dev tools (ESLint, Prettier, Vitest; Node 22.12+).

```bash
npm ci                                       # install the dev tools
npm run check                                # lint, format check and tests: run before every commit
npm test                                     # tests only (npm run test:watch while working)
npm run test:rules                           # database rules tests in the Firebase emulator (needs Java 11+; CI runs them too)
npm run test:e2e                             # browser test: builds _site, makes and runs a routine at phone size, reloads offline (once: npx playwright install chromium)
npm run format                               # apply Prettier
npm run tokens                               # write tokens.css after changing design/tokens.json
bash build.sh _site                          # build the site (decodes icons/fonts from base64)
python3 -m http.server 8000 -d _site         # run it at http://localhost:8000 (ES modules don't work over file://)
for f in core/*.js ui/*.js cloud.js sw.js; do node --check "$f"; done   # syntax check
node -e "import('./core/schedule.js').then(m=>console.log(Object.keys(m)))"  # load a core module in Node
```

Rebuild `_site` after every change; it is a build output, never commit it.

Prettier formats all code (`npm run format`). Formatting-only commits go in `.git-blame-ignore-revs` so `git blame` skips them; run `git config blame.ignoreRevsFile .git-blame-ignore-revs` once locally.

## Layout

- `index.html`: the page and all views. Loads `tokens.css`, `styles.css` (all CSS) and `ui/main.js`. `privacy.html`: the privacy policy, a static page without scripts; update it (and its date) when what's stored or who processes it changes. For search engines and link previews, each page names its `https://punchpace.app/…` address as canonical (the old addresses serve the same files), `index.html` has the Open Graph tags, and `robots.txt` and `sitemap.xml` sit at the root: add a new page to the sitemap. `favicon.ico` and the preview image `og-image.png` (1200×630) are base64 in `icons/`, like the install icons.
- `design/`: the design tokens (`tokens.json`: colours, spacing, type, radii, durations), the script that writes `tokens.css` from them, and the design rules (`design/README.md`).
- `core/`: app logic with no DOM or browser APIs, so it runs in Node. Routine model and migrations (`routine.js`), days, parts of the day, up next and streaks (`schedule.js`), the step list, boxing moves (stable ids) and combo tones (`steps.js`), timer engine (`engine.js`), voice timing (`voice.js`), sync merge and the items the account stores (`merge.js`), moving data from the old addresses (`move.js`), durations and dates (`time.js`), what another open window's storage change means (`windows.js`: anything that clears this device's data writes `WIPE_KEY` so the other windows reload), problem reports from Settings → About (`report.js`: the text and the email and issue links; never routines or account details. `ui/errors.js` keeps the last errors in memory for it).
- `ui/`: everything on screen and on the device: views, editor, run screen, settings, history, sound and voice, storage, sync.
- `cloud.js`: Firebase Auth + Realtime Database, loaded only after sign-in or opening Settings. The config in it is public; access is limited by `database.rules.json`. Sign-in runs through `punchpace.app` (`authDomain`, the security policy's `frame-src`) from every address the app runs on; each address must be in Firebase Auth's Authorized domains and allowed on the API key. The Google and GitHub OAuth apps redirect to `https://punchpace.app/__/auth/handler`. App Check (`APP_CHECK`: a reCAPTCHA site key, public) proves requests come from the app's own pages; it and the database start only once someone is signed in, so signed-out visitors never load reCAPTCHA (the privacy policy says so); reCAPTCHA needs `https://www.google.com` in the policy's `script-src`, `frame-src` and `connect-src`. Testing locally against the real database: set `APP_CHECK_DEBUG` and add the printed token in Firebase → App Check. The browser API key only allows the Identity Toolkit, Token Service and Firebase App Check APIs, from the app's own addresses. Changing the rules: update `test/rules/` and run `npm run test:rules`. The project is on the Blaze plan: a budget in Google Cloud Billing (Budgets and caps) emails the billing admin at €5, €20 and €50 a month. The Realtime Database is backed up daily to the bucket `workout-pacer-default-rtdb-backups` (Belgium); a lifecycle rule deletes backups after 30 days, soft delete keeps them 7 more, and `privacy.html` says so: change it with them. Restoring: download a backup from Realtime Database → Backups and import it into a new, empty database instance to check it; import over the live database only to recover from a fault, and only after taking a manual backup first.
- `docs/multi-device.md`: the model of a running workout across devices and windows (controller and followers, what each control does) and its edge cases, expected vs actual. Read it before changing `ui/runner.js` or the run parts of `ui/sync.js`, and update it with them; `test/e2e/devices.test.js` covers the cases that behave as described.
- `schema/routine.schema.json`: the routine format (JSON Schema), versioned by `cv`. Served with the site.
- `test/`: Vitest tests for `core/`, one file per module (`<module>.test.js`). Tests run in the `Europe/Amsterdam` time zone (`vitest.config.js`) because dates are local time. `test/rules/` tests `database.rules.json` against the Realtime Database emulator (`firebase.json`, `vitest.rules.config.js`, project `demo-punchpace`); `npm test` skips it. `test/e2e/` is the Playwright browser test (`playwright.config.js`): it builds and serves `_site` on port 4173, then at phone size makes a routine, starts it, stops it and reloads offline, and fails on any console error (CSP violations included); `npm test` skips it too. `devices.test.js` runs one workout on two devices (browser contexts) without Firebase: it serves `test/e2e/fake-cloud.js` in place of `cloud.js`, which shares the running workout between them. The stand-in doesn't check the database rules, so a new or changed run field also needs a rules test. `a11y.test.js` opens every screen and fails on a control with a tap area under 44px or text under 4.5:1 contrast (axe-core, injected with the security policy bypassed for that test only), on anything sticking out sideways at 320px wide with the text at 200%, on run screen parts that overlap on a short screen with the text at 200%, and on a flash or pop under reduce motion.
- `eslint.config.js`: lint rules per folder; it reads the element ids from `index.html` because `ui/` uses them as globals.
- `sw.js`: offline cache. `build.sh`: build script (also names the offline cache after the commit, and writes the version and commit into Settings → About). `.github/workflows/deploy.yml`: runs `npm run check`, `npm run test:rules` and `npm run test:e2e` on pull requests and on `main`. Only when all three pass it deploys `main`: first the database rules (`npm run deploy:rules`, in the `firebase` job just before Hosting), then GitHub Pages and Firebase Hosting (https://punchpace.app and https://workout-pacer.web.app; the domain's DNS is at Namecheap: an A record and a `hosting-site` TXT record for Firebase, next to the email-forwarding records), and each pull request to the one Firebase preview channel `preview`, whose link is commented on the PR (needs the `FIREBASE_SERVICE_ACCOUNT_WORKOUT_PACER` secret; skipped without it, e.g. for Dependabot). The preview has one fixed address (`workout-pacer--preview-<hash>.web.app`) and shows the most recently pushed PR; that address is allowed once, like the others, in Firebase Auth's Authorized domains, on the browser API key and on the reCAPTCHA key, so sign-in works there. The channel expires 30 days (Firebase's maximum) after the last PR deploy; the next PR then gets a new hash, which has to be allowed again in those three places. Hosting settings and headers (security headers including the Content Security Policy, `no-cache` for code so the offline worker gets updates) are in `firebase.json`. The deploy key (service account in the secret) has Hosting's roles plus a custom role, _Database rules deployer_, with only `firebase.projects.get`, `firebasedatabase.instances.get` and `firebasedatabase.instances.update` (what `firebase deploy --only database` checks), instead of the broad Realtime Database Admin. Whoever can publish rules can also open the database with them, so treat the key as an admin key; it lives only in the repo secret. Don't publish rules in the console: the next merge overwrites them. Pull requests never publish rules; a preview runs against the live rules. `.github/dependabot.yml`: weekly update PRs for the dev tools and actions (the Firebase SDK version in `cloud.js` and the firebase-tools version in `test:rules` and `deploy:rules` are updated by hand). Secret scanning, Dependabot alerts and CodeQL code scanning are on in the repo settings.

## Rules

- **Pushing to `main` deploys to the live app.** Work on a branch and open a PR; don't push to `main` unless asked.
- `core/` only imports from `core/`. `ui/` calls into `core/`, never the other way round. Pass state into core functions instead of reading globals.
- No inline code: the Content Security Policy blocks `onclick="…"` and other inline handlers and `<script>` blocks. Buttons and fields name an action instead: `data-on="click:startRun"` in `index.html`, `${does('click:startRun', r.id)}` in HTML built in `ui/`; register the action in `ui/main.js` (`plainActs`, or `acts` when it needs the element). See `ui/actions.js`. `test/csp.test.js` fails on inline handlers.
- A new external host (a script, an API, a sign-in domain): add it to the policy in both `firebase.json` (header) and the `<meta>` tag in `index.html` (for GitHub Pages); `test/csp.test.js` checks they match.
- New or renamed file the app loads: add it to `FILES` in `sw.js`, or the app breaks offline. Don't edit `CACHE`: `build.sh` names it after the commit, so every deploy refreshes the offline cache.
- Never rename storage keys (`rf2_*`) or synced paths (`users/<uid>/v2/…`, `users/<uid>/run`, and the old `users/<uid>/doc`, read once to move an account): it would lose people's data.
- No unclaimed names (domains, organizations, handles) in issues, PRs, commits or code: keep them on _Platforms & accounts_ in Notion until they're claimed.
- Sync stores one item per routine and workout (`users/<uid>/v2/routines/<id>`, `…/history/<id>`, plus `order`, `parts`, `since`), each with `m`, when it was written. A device asks only for items written since it last looked (`rf2_synced`), so a change to sync should keep downloads to what changed. The rules for which version wins live in `core/merge.js` (`merge`, `newer`; for the running workout `runWins`: `setRun` in `cloud.js` writes it in a transaction that only replaces a version the device knew about, and the database rules refuse a write to the same workout whose `u` isn't higher); `database.rules.json` indexes `m`. The database rules also check the shape and size of every write (only known keys, types, size limits), so a new synced field or path, including in `users/<uid>/run`, needs a rule and a test in `test/rules/`, or its writes are refused. CI publishes the rules just before the app on Firebase Hosting, so both can change in one PR; a rule that refuses something the app used to write also refuses devices still on the older version until they update (#55).
- Changing the routine data shape: update `schema/routine.schema.json`, add a step to `MIGRATIONS` in `core/routine.js` and bump `CV` (the schema's `cv`), so old routines, exports and other synced devices keep working. `test/schema.test.js` checks that routines are valid. Sync merges across devices (`core/merge.js`), so new fields need a sensible merge.
- Use the design tokens, never hard-coded values: colours by role (`--text-muted`, `--surface`, `--accent-text`, `--routine-blue`), spacing on the 4px grid (`--space-3`), the type scale (`--fs-sm`), `--radius-*`, `--duration-*`. Follow the rules in `design/README.md` (contrast, scales, touch targets); `test/tokens.test.js` checks the colour ones. A light theme is planned, so don't assume dark.
- Repeated inline styles become classes (the utilities at the end of `styles.css`).
- Follow the existing style: Prettier formatting, a short comment at the top of each module saying what it does, comments that explain _why_.
- Update `README.md` when a user-facing feature changes.
- `CONTRIBUTING.md` is the short version of these rules and commands for contributors: keep it in step when they change.

## UX and copy

- Guidance guides, it doesn't enforce: features like parts of the day and Up next suggest an order; users can ignore them or switch them off in Settings.
- UI text is plain and short. Step cues say what to do ("Right knee: lift forward, swing out, down"), not exercise jargon.
- Voice, separators (`·`, `×`), times, icons and the logo: follow `design/README.md`.
- Check changes on a phone-sized screen; it's mostly used on Android as an installed app.

## Workflow

- Work comes from GitHub issues (templates in `.github/ISSUE_TEMPLATE/`: _Planned change_ with Problem / Proposal / Done when and one kind label; forms _Something's wrong_ and _I have an idea_ for people who don't code; PR template in `.github/pull_request_template.md`). Phases are milestones; each issue has one row on the PunchPace board in Notion.
- One issue per session. For anything beyond a small fix, plan first and check the plan before coding.
- Changing `core/`: add or update its tests in `test/`.
- Before finishing: `npm run check`, build, run it, check the change in the browser (including offline if `sw.js` changed). Changed `ui/`, `index.html`, `sw.js` or the security policy: also `npm run test:e2e`, and update it when the flow it follows changes.
- Commit subjects describe what changes for the user, in plain words, e.g. "Up next label back on the home screen, quieter outline for the other routines". Reference the issue (`#27`) in the PR.
- Releases (from launch on: 1.0, 1.1, … one per release milestone): the version lives only in `package.json` (`npm version 1.1.0 --no-git-tag-version`), `build.sh` writes it and the commit into Settings → About. After the version PR is merged, tag the commit `v1.1` and publish a GitHub Release with generated notes, edited for users. Steps in `CONTRIBUTING.md` (_Releases_). The routine format's `cv` is a separate version.
